# Sizeup2 M3 — Settings, persistence, and a Preferences window

Plan date: 2026-08-14. Branch: `m3-settings`, off `main @ 9063d03`.
Prerequisite: M2 merged (`21232e1`), 125 tests passing.

## Why this milestone exists

Three features were promised beyond SizeUp parity: **size cycling**, **configurable gaps**, and a
**per-app skip list**. All three are already implemented in the geometry layer and all three are
currently **unreachable**, because `AppDelegate` hardcodes:

```swift
gaps: .zero,
spans: [.half],
skipList: []
```

`spans: [.half]` means the size cycle has exactly one step, so cycling is a no-op. M3's job is not to
write new window math — `targetFrame` already handles gaps and spans exactly, verified below. M3's job
is to build the **configuration boundary** that lets a user reach that math, and to make that boundary
refuse to produce a broken window.

## Scope decisions

### The SizeUp plist import is deferred, and this is a reversal

The M2 handoff said M3 owns it. Having looked at what the plist actually contains, that was wrong.
Stripped of shortcuts, the user's live SizeUp plist holds exactly this:

```
MinutesSaved => 666        ShortcutsDisabled => false
WindowsMoved => 13320      ShowPrefsOnNextStart => false
                           SULastCheckTime => 2026-08-13
```

Nothing worth importing. **All of the plist's value is in its shortcut bindings — and those are
already hardcoded into `DefaultKeymap`, derived from this very file, and pinned by
`matchesTheUsersSizeUpConfiguration`.** Importing them would compute a value we already have.

The import only becomes meaningful once shortcuts are **rebindable**, because only then is there
somewhere for imported values to go. Rebinding needs a key-capture control and the `keyName`
`UCKeyTranslate` work, which is a milestone of its own. So:

- **M3** — settings, persistence, Preferences window for gaps / cycling / skip list.
- **M4** — shortcut rebinding, then SizeUp import (which is ~30 lines once rebinding exists).
- **M5** — Spaces (was M4).

Building the import now would mean building it twice: once against a hardcoded keymap it cannot
affect, and again against the real one.

### Cycling must default to OFF

The user has 13,318 window moves of muscle memory. Today, pressing ⌃⌥⌘← twice leaves the window a
left half. If cycling shipped enabled by default, the second press would resize it — a silent change
to the single most-used shortcut in the app.

**Default `spans` stays `[.half]`.** Cycling is opt-in. The default `Settings()` must reproduce
current behaviour byte-for-byte; a test asserts this against the same values `AppDelegate` hardcodes
today.

### Gaps must be capped, because an uncapped gap makes a zero-width window

Measured against the real compiled `Geometry`, on a 100×100 display:

| gaps | `targetFrame(.fullScreen)` | `targetFrame(.half(.left))` |
|---|---|---|
| `outer: 60` | `nil` — the `usable.width > 0` guard fires | — |
| `inner: 500` | — | **`(0, 0, 0, 100)` — width zero** |

The outer case is already safe: `targetFrame` returns `nil` and the router does nothing. The inner
case is **not** — it returns a real rect of zero width, and `isSafeToApply` permits it (`width >= 0`),
so we would write a zero-width window that the user cannot grab. That is the same class of harm as the
NaN frame M2 guarded.

**Both gaps clamp to `0...100`.**

> **Corrected after the final review.** This section originally argued that the clamp alone closed the
> hazard, so `isSafeToApply` need not change — reasoning that a 1024pt display still yields a 462pt half
> at `inner: 100`. That arithmetic assumed **two** columns. With the 12 columns the validator accepts,
> `inner: 100` consumes 1100pt of an 1055pt axis and the bottom half comes out **zero-height** on a
> 1080p display, which `isSafeToApply` then permitted. The clamp is kept, but the real fix is that
> `targetFrame` refuses a degenerate result and `isSafeToApply` now requires a strictly positive size.
> A configuration-boundary check was the wrong place for this, because the hazard depends on the
> display, not only on the setting.

### Non-goals for M3

- Shortcut rebinding, and therefore the SizeUp import (M4).
- Spaces (M5).
- Per-app rules beyond a skip list — the spec settled on skip-list-only.
- Anything that changes default behaviour. M3 adds reachability, not new defaults.

## Architecture

A new target, `Config`, sitting between `Geometry` and the app:

```
Geometry ── Config ── App
   └────── Core ────────┘
```

`Core` does **not** depend on `Config`. `ActionRouter` keeps its existing explicit
`gaps` / `spans` / `skipList` parameters, and `App` translates settings into them. This matters for
two reasons: the router stays testable without a config layer, and it keeps `Config` free to hold
UI-shaped types that the router should never see.

**Live updates rebuild the router rather than mutating it.** `ActionRouter`'s only mutable state is
the injected `WindowStateStore`; everything else is configuration. So a settings change can construct
a fresh router with the same store, and no window loses its Snap Back origin. This is simpler than
making six properties mutable and cannot go half-applied.

**`Config` defines its own Codable DTOs** rather than conforming `Gaps` and `Span` to `Codable`.
Retroactive conformance across modules needs `@retroactive` in Swift 6 and would put a serialization
format in the geometry layer. More importantly, a DTO gives us the place the deferred findings ask
for: `Span.init` traps on bad input via `precondition`, so **the DTO validates and returns nil rather
than letting user configuration reach a trapping initializer.**

## Task 1 — `Settings` model with a validating decode

**Files:** `Sources/Config/Settings.swift`, `Tests/ConfigTests/SettingsTests.swift`,
`Package.swift`.

Add the `Config` target (depends on `Geometry`) and `ConfigTests`.

```swift
public struct Settings: Sendable, Equatable, Codable {
    public var gaps: GapSettings
    public var cycle: [SpanSetting]
    public var skippedBundleIdentifiers: [String]
}
```

`GapSettings { inner, outer }` and `SpanSetting { occupied, columns }` are plain `Codable` structs.
Each exposes a conversion into the `Geometry` type:

- `GapSettings.resolved: Gaps` — clamps both values into `0...100`, and clamps NaN to 0.
- `SpanSetting.resolved: Span?` — `nil` unless `columns` is in `2...12` and `occupied` is in
  `1..<columns`. Note `occupied < columns`, not `<=`: a span covering every column is a full screen,
  not a cycle step, and admitting it would put a useless step in the user's cycle.
- `Settings.resolvedCycle: [Span]` — maps, drops nils, and **falls back to `[.half]` if the result is
  empty**, so an all-garbage cycle list cannot produce the empty array that `ActionRouter` would
  silently coerce anyway. Doing it here means the router's coercion stops being load-bearing.

### Tests (RED first)

1. `defaultSettingsReproduceTodaysHardcodedBehaviour` — `Settings()` has `resolved == Gaps.zero`,
   `resolvedCycle == [.half]`, empty skip list. **This is the muscle-memory guard**; it must name that
   in a comment.
2. `aSpanCoveringEveryColumnIsRejected` — `SpanSetting(occupied: 2, of: 2).resolved == nil`.
3. `aZeroColumnSpanIsRejectedRatherThanTrapping` — `SpanSetting(occupied: 1, of: 0).resolved == nil`.
   Comment must state that `Span.init` would `precondition`-trap on this, which is why the DTO exists.
4. `oversizedGapsAreClampedNotHonoured` — `GapSettings(inner: 500, outer: 500).resolved` gives
   `Gaps(inner: 100, outer: 100)`. Comment: measured, an inner gap of 500 produces a **zero-width**
   window on a small display.
5. `negativeGapsClampToZero`.
6. `nonFiniteGapsClampToZero` — `.nan` and `.infinity` both land on a finite value. (`min`/`max` are
   not NaN-quieting; M2 already learned this.)
7. `anAllInvalidCycleFallsBackToHalves` — cycle of three invalid spans resolves to `[.half]`.
8. `aPartiallyInvalidCycleKeepsTheValidSteps` — `[1/2, 5/3, 1/3]` resolves to `[half, 1/3]` in order.
9. `settingsRoundTripThroughJSON` — encode then decode is `Equatable`-identical.
10. `decodingToleratesMissingFields` — `{}` decodes to defaults. Requires `init(from:)` to
    `decodeIfPresent` each field; a plain synthesized `Codable` throws here, so this test drives real
    code, not a formality.

## Task 2 — `SettingsStore`: persistence that cannot lose or crash

**Files:** `Sources/Config/SettingsStore.swift`, `Tests/ConfigTests/SettingsStoreTests.swift`.

```swift
public final class SettingsStore {
    public init(url: URL)                       // injectable for tests
    public static var defaultURL: URL           // ~/Library/Application Support/Sizeup2/settings.json
    public private(set) var settings: Settings
    public func load()
    public func save(_ new: Settings) throws
}
```

Requirements:

- **Load is total.** A missing file, an unreadable file, malformed JSON, or JSON of the wrong shape all
  yield `Settings()` and never throw. A window manager that refuses to start because its config is
  corrupt is worse than one that starts with defaults.
- **Save is atomic** — write to a sibling temp file, then `replaceItemAt`. A crash mid-write must not
  leave a truncated file, because the next load would silently reset every preference.
- Creates the containing directory if absent.
- JSON is pretty-printed with sorted keys, so the file is hand-editable and diffable. This is a real
  requirement, not polish: hand-editing is the only way to reach spans the UI does not offer.

### Tests

1. `loadingAMissingFileYieldsDefaults`.
2. `savedSettingsSurviveAReload` — save non-default values through one store, read with a second store
   at the same URL.
3. `loadingCorruptJSONYieldsDefaultsWithoutThrowing` — write `"{ not json"`.
4. `loadingJSONOfTheWrongShapeYieldsDefaults` — write `{"gaps": "huge"}`.
5. `loadingCreatesNoFile` — reading must not write; asserts the file still does not exist afterwards.
6. `savingCreatesTheContainingDirectory` — URL two levels below a fresh temp dir.
7. `aSecondSaveDoesNotLeaveATempFileBehind` — the directory holds exactly one file afterwards. This is
   the test that would catch a botched atomic replace.
8. `theSavedFileIsHumanReadable` — the on-disk bytes contain `"inner"` and a newline.

Each test uses its own `FileManager.default.temporaryDirectory.appendingPathComponent(UUID())` and
removes it afterwards.

## Task 3 — make the settings reach the router

**Files:** `Sources/App/AppDelegate.swift`, `Sources/Core/WindowStateStore.swift`, `Package.swift`.

1. `App` gains a dependency on `Config`.
2. `AppDelegate` owns a `SettingsStore`, calls `load()` before building the router, and passes
   `settings.gaps.resolved`, `settings.resolvedCycle`, `Set(settings.skippedBundleIdentifiers)`.
3. Extract `rebuildRouter()`, called at launch and after any settings change. It must **reuse the
   existing `store`**, so Snap Back origins survive a preferences change.
4. Deferred finding: raise `WindowStateStore` capacity 50 → 200. Evicting a Snap Back origin the user
   still remembers is worse than the memory, and `touch()` being O(n) is irrelevant at either size.
   Update the capacity test.

No new tests for `AppDelegate` (still untested by design, still covered by the AX runtime check). The
`WindowStateStore` capacity change updates an existing test.

## Task 4 — the Preferences window

**Files:** `Sources/App/PreferencesWindow.swift`, `Sources/App/PreferencesView.swift`.

SwiftUI in an `NSWindow` via `NSHostingController`. SwiftUI because this is a static form and AppKit
would be ~4× the code for the same result.

Three sections in one pane — tabs would be premature for nine controls:

**Gaps.** Two steppers with numeric fields, `0...100`, step 2, labelled "Between windows" and
"Screen edges" rather than "inner"/"outer". A live preview is out of scope.

**Size cycling.** The catalogue approach, not a free-form editor. A fixed ordered list of common spans
— ½, ⅓, ⅔, ¼, ¾ — each with a checkbox, applied in that canonical order. Rationale: a free-form
`occupied/columns` editor exposes exactly the invalid combinations Task 1 has to defend against, and
asks the user to think in a model they did not choose. Anything the catalogue cannot express is
reachable by hand-editing the JSON, which is why Task 2 requires it be readable. Must show explicit
text that with only ½ selected, repeated presses do not resize — otherwise the default looks broken.

**Skip list.** A `List` of bundle identifiers with `+` / `−`. `+` presents the currently-running
regular applications (`NSWorkspace.shared.runningApplications` filtered to
`.activationPolicy == .regular`, sorted by localized name), because no user knows bundle identifiers
by heart. Display the app name with the identifier as a subtitle.

Writes go through a small `@MainActor @Observable` view model that calls
`store.save(_:)` and then the injected `onChange` closure, which is `rebuildRouter`.

Save-on-edit, not an OK/Cancel pair: there is nothing here whose half-applied state is dangerous, and
a menu-bar app has no natural moment to press OK.

### Tests

None. This is `AppDelegate`-class untestable UI, and the honest move is to say so rather than write
tests that assert SwiftUI compiles. The view **model** is where logic could hide, so it must be kept
free of logic — all validation lives in `Config` and is tested there. Verified instead by the Task 7
runtime check and the manual checklist.

## Task 5 — reaching the window

**Files:** `Sources/App/AppDelegate.swift`.

1. Menu item **"Settings…"** with key equivalent `,` and `.command`, placed above "Open at Login".
2. Opens a single reused window: if it already exists, `makeKeyAndOrderFront` and do not build a
   second one. Two preferences windows editing the same file is a lost-update bug.
3. `NSApp.activate()` first — an `LSUIElement` app is not active, so without this the window appears
   behind whatever the user was using.
4. Window is `.titled, .closable`, not resizable, `center()`ed on first open, and its close must not
   terminate the app.
5. `menu.autoenablesItems` is `false` (M2), so the new item needs `isEnabled = true` explicitly. **This
   is the third instance of this exact bug** — M1's dead menu, M2's dead login item — so the plan calls
   it out rather than trusting it to be remembered.

## Task 6 — close the M3 deferred findings

**File:** `docs/superpowers/M1-deferred-findings.md`.

Move to "Closed in M3", each with what actually resolved it:

- `Span.init` `precondition` — now unreachable from configuration; `SpanSetting.resolved` returns nil.
- `ActionRouter` coercing empty `spans` — now belt-and-braces; `resolvedCycle` never returns empty.
- `WindowStateStore` capacity 50 → 200.

Record as newly deferred:

- ~~`isSafeToApply` permits a zero-size rect; safety rests on the gap clamp.~~ **Wrong, and corrected
  during the final review** — see the blockquote under "Gaps must be capped". The clamp is not a safety
  mechanism; `targetFrame` and `isSafeToApply` reject degenerate placements directly.
- The gap cap of 100 remains a judgement, not a derivation. It is **not** claimed to be safe for any
  particular display size.
- A *valid* span can still be degenerate for a given display and gap (1/12 at `inner: 100` on 1080p).
  That shortcut becomes a silent no-op, with no warning in the UI, because the placement is refused at
  the geometry layer where there is nothing to warn through. Correct in preference to moving the window
  wrongly, but undocumented for the user.
- `proportionalFrame` still ignores gaps (carried from M2, now genuinely reachable since gaps can be
  non-zero — a hand-positioned window moved between displays will not be inset while a tiled one is).
  **This one is now a real inconsistency rather than a hypothetical**, and should be stated as such.

## Verified values

Measured against the compiled `Geometry` on the built-in display
(`visibleFrame = (0, 0, 3360, 1860)`), for use as expected values:

| gaps | left half | right half | seam |
|---|---|---|---|
| `0/0` | `(0, 0, 1680, 1860)` | `(1680, 0, 1680, 1860)` | 0 |
| `inner 10, outer 10` | `(10, 10, 1665, 1840)` | `(1685, 10, 1665, 1840)` | 10 |
| `inner 0, outer 20` | `(20, 20, 1660, 1820)` | `(1680, 20, 1660, 1820)` | 0 |
| `inner 12, outer 0` | `(0, 0, 1674, 1860)` | `(1686, 0, 1674, 1860)` | 12 |

With `inner 10, outer 10`: full screen `(10, 10, 3340, 1840)`, upper-left quarter
`(10, 935, 1665, 915)`, lower-right `(1685, 10, 1665, 915)`. Cycle widths for a left half:
½ → 1665, ⅔ → 2223, ⅓ → 1106.

The seam between complementary halves equals the inner gap exactly at every gap tested, which is what
the `Span` column model was introduced to guarantee.
