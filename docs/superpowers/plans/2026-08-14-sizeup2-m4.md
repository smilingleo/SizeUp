# M4 — Shortcut rebinding, then the SizeUp import

## Why this milestone exists

Every shortcut is currently a literal in `DefaultKeymap.swift`. That was correct for M1–M3: the
bindings were copied from the user's own SizeUp plist, so they were right by construction and nobody
needed to change them. It stops being correct the moment anyone else runs this, or the moment the user
wants a different key — and it is the last thing standing between this app and being usable by someone
who is not its author.

The SizeUp import comes second, in the same milestone, because it has nowhere to put anything until
rebinding exists. Stripped of shortcuts, that plist contains `MinutesSaved`, `WindowsMoved`, two
booleans and a toolbar layout; the import *is* the shortcut import.

## What ships

- Every action's shortcut is rebindable, and can be unbound.
- Real key names for every key, not `"?"`.
- Conflicts are resolved visibly, never silently.
- A one-click import from an installed SizeUp.
- Defaults unchanged. A user who never opens the Shortcuts tab sees exactly M3's behaviour.

## Design decisions

### Store overrides, not a keymap

`Settings.shortcutOverrides: [ShortcutSetting]`, merged over `DefaultKeymap.bindings`.

The obvious alternative — persist the whole resolved keymap — is wrong in a way that only shows up
later. M5 adds four Spaces actions. A user who had saved a full keymap under M4 would have a file that
does not mention them, and the natural reading of "the file is the keymap" is that anything absent is
unbound. They would get an app with no Spaces shortcuts and no indication why. Overrides degrade
correctly: unmentioned actions keep whatever default the current version ships.

It is also much easier to read. A user who rebinds one key gets a one-entry array, not a
seventeen-entry dump they have to diff against the defaults to understand.

`keyCode: nil` means **deliberately unbound**, which is distinct from "not mentioned". Without this
there is no way to turn a shortcut off, and turning one off matters: these are global hotkeys, and
⌃⌥⌘M is not free if you use it for something else.

### Actions are identified by string, not by Swift's synthesized coding

`"half.left"`, `"quarter.upperLeft"`, `"space.next"`. `Action` has associated values, so the
synthesized `Codable` conformance produces nested objects that are unpleasant to hand-edit and, worse,
are coupled to the case declaration order and spelling. A stable string table is the whole point of a
DTO layer, and it gives unknown identifiers an obvious place to be ignored rather than to throw.

Consistent with M3: `Config` owns the mapping. `Geometry` does not learn about persistence.

### The merge lives in `Core`, not in `App`

`Core` must not depend on `Config` (M3), and `Config` must not depend on `Hotkeys` — configuration has
no business importing Carbon. So the merge takes a `Core`-local `ShortcutOverride` value and `App`
performs the trivial DTO translation.

This is the same trade M3 made for `Span`/`SpanSetting`, for the same reason: a boundary translation
that is obviously correct by inspection is a better cost than a dependency edge that lets persistence
concerns leak into the domain. The part with actual logic in it — merging, and conflict detection — is
tested. `App`'s share is a `compactMap`.

### Conflicts unbind the previous owner, and say so

Two actions cannot hold one shortcut: `RegisterEventHotKey` fails for the second, which the existing
`RegistrationFailure.alreadyClaimedByThisApp` already reports. But arriving at that state through the
UI is a defect, not a diagnostic.

When a recorded shortcut is already held, the previous owner is unbound and the UI names it. The
alternative — refusing the new binding — reads as the recorder being broken, because the user pressed
keys and nothing happened. Reassigning silently is worse than either: a shortcut the user relies on
stops working with no explanation. macOS System Settings behaves the same way.

### Hotkeys must be suspended while recording

**The trap in this milestone.** A registered Carbon hotkey consumes the keystroke before the focused
application sees it. So a recorder built on `NSEvent.addLocalMonitorForEvents` cannot observe
⌃⌥⌘← — pressing it during recording *moves the Preferences window to the left half* instead. The
user cannot rebind any shortcut that is currently bound, which is the overwhelmingly common case.

`HotkeyManager.unregisterAll()` before recording, re-register after. Recording is therefore a mode with
a visible beginning and end, not an always-live monitor.

### At least one of Control, Option or Command is required

A global hotkey with no modifier steals that key from the entire system, and one with only Shift steals
a capital letter. Neither is recoverable from inside the app if the user binds something like plain `A`.
Validated in `Config`, where invalid entries are already dropped rather than trusted.

### Key names come from the keyboard layout, with a table for the keys layouts lie about

`UCKeyTranslate` returns control characters for Return, Tab, Escape, arrows and the F-keys, so those
come from a static table. Everything else is translated against the current layout, so a Dvorak or AZERTY
user sees the key they actually press. The table is tested; `UCKeyTranslate` is asserted only where every
Latin layout agrees.

## Tasks

### Task 1 — Real key names

`Sources/Hotkeys/KeyName.swift`. `KeyName.of(_ keyCode: UInt32) -> String`.

Static table for: arrows (123–126), Return 36, Tab 48, Space 49, Delete 51, Escape 53, Forward-Delete
117, Home 115, End 119, PageUp 116, PageDown 121, F1–F12, and the keypad. Then `UCKeyTranslate` against
`TISCopyCurrentKeyboardInputSource`'s `kTISPropertyUnicodeKeyLayoutData`, uppercased. Fall back to
`"Key \(keyCode)"` — never `"?"`, which tells the user nothing and is indistinguishable between "we
cannot name this" and "the key is literally `?`".

`Shortcut.keyName` delegates here and the private table in `Shortcut.swift` is deleted.

**Tests:** every table entry; that a letter key yields one uppercase Latin character; that an absurd
keycode yields the `"Key N"` form and not `"?"`; that `displayString` for the shipped defaults still
reads exactly `⌃⌥⌘←`, `⌃⌥⌘M`, `⌃⌥⌘/`, `⌃⌥⇧↑`, `⌃⌥→`.

### Task 2 — `ShortcutSetting` and the action identifier table

`Sources/Config/ShortcutSetting.swift`.

```swift
public struct ShortcutSetting: Codable, Equatable, Sendable {
    public let action: String        // "half.left"
    public let keyCode: UInt32?      // nil == deliberately unbound
    public let modifierFlags: UInt
}
```

`ActionIdentifier.action(for: String) -> Action?` and `.identifier(for: Action) -> String`, exhaustive
over all 15 actions, round-tripping.

`ShortcutSetting.resolved -> (action: Action, keyCode: UInt32?, modifierFlags: UInt)?`, returning nil
when the identifier is unknown, or when a non-nil keyCode carries no Control/Option/Command.

`Settings.shortcutOverrides: [ShortcutSetting] = []`.

**Tests:** round-trip for all 15 actions; unknown identifier resolves to nil rather than throwing;
Shift-only and bare keycodes resolve to nil; an unbind entry (`keyCode: nil`) resolves *successfully*
with a nil keyCode — this is the distinction the whole feature rests on, so it needs its own test;
`Settings()` has no overrides; a settings file containing overrides decodes.

### Task 3 — Merging overrides over the defaults

`Sources/Core/KeymapResolver.swift`.

```swift
public struct ShortcutOverride: Equatable, Sendable {
    public let action: Action
    public let keyCode: UInt32?
    public let modifierFlags: UInt
}

public struct ResolvedBinding: Equatable, Sendable {
    public let action: Action
    public let shortcut: Shortcut?   // nil == unbound
}

public enum KeymapResolver {
    public static func resolve(overrides: [ShortcutOverride]) -> [ResolvedBinding]
    public static func conflicts(in: [ResolvedBinding]) -> [Shortcut: [Action]]
}
```

`resolve` starts from `DefaultKeymap.bindings`, applies overrides by action, and — because a user can
override two actions onto one key by hand-editing — resolves any remaining conflict by keeping the
**first** in `DefaultKeymap` order and unbinding the rest, so the result is always registrable.
`conflicts` reports what the file asked for, so the UI can explain it.

Every action appears in the result exactly once, in `DefaultKeymap` order, including actions with no
override and including unbound ones.

**Tests:** no overrides reproduces `DefaultKeymap.bindings` exactly; one override changes one binding
and nothing else; an unbind yields a nil shortcut and every other action survives; a hand-edited
conflict leaves exactly one action holding the key and reports both; a later override wins over an
earlier one for the same action; an override for an action not in the defaults is ignored rather than
appended. Assert against `DefaultKeymap` rather than local literals — M2 shipped two tests that
compared literals to each other and could not fail.

### Task 4 — Wiring

`App`: translate `Settings.shortcutOverrides` to `[ShortcutOverride]`, resolve, register. On settings
change, `unregisterAll()` then re-register. `suspendHotkeys()` / `resumeHotkeys()` for the recorder.

The status menu's shortcut labels must come from the resolved keymap, not from `DefaultKeymap`, or the
menu will confidently display the wrong keys after any rebind.

**Tests:** none directly (this is `AppDelegate`, untested by construction). Covered by Task 3 and the
manual checklist, and stated as such.

### Task 5 — The Shortcuts tab

`Sources/App/ShortcutsView.swift`, a new tab in the Preferences window.

One row per action: name, current shortcut, a record button, a clear button. Recording shows "Press
keys…", suspends the global hotkeys, takes the next key-down with a valid modifier combination, and
resumes. Escape cancels. A conflict unbinds the previous owner and shows an orange line naming it.
"Restore Defaults" clears all overrides.

Judgements to make in code, not to be surprised by later: modifier-only key-downs must not end
recording; the button must return to its resting state if the window closes mid-recording, or the
hotkeys stay suspended and the app silently stops working.

**Verification: screenshot the live window.** M3's four UI defects were all invisible to code review
and to the implementer's own report, and one of them made a control unreachable. A report claiming this
tab works is not evidence.

### Task 6 — The SizeUp import

`Sources/Config/SizeUpImport.swift`. Reads a plist at a given URL — injectable, so the fixture is
testable — and returns `[ShortcutSetting]`.

Mapping, taken from the real file and not from memory:

| SizeUp key | Action |
|---|---|
| `Left` `Right` `Up` `Down` | `half.left` `half.right` `half.top` `half.bottom` |
| `Upper Left` `Upper Right` `Lower Left` `Lower Right` | the matching `quarter.*` |
| `Full Screen` `Center` `SnapBack` | `fullScreen` `center` `snapBack` |
| `Next Monitor` `Prev Monitor` | `display.next` `display.previous` |
| `Space Next` `Space Prev` `Space Above` `Space Below` | the matching `space.*` |

Each entry is a dict with `ComboCode` and **`ComboFlags`** — not `ComboModifiers`; the name was read
off the real file. Entries that are absent, malformed, or carry no real modifier are skipped, and the
result reports how many were imported and how many skipped, so a partial import cannot look like a
complete one.

Menu item: "Import from SizeUp…", enabled only when the plist exists.

**Tests:** against `Tests/Fixtures/sizeup-user-config.plist`, all 17 map to the right actions with the
right codes and flags; a missing file yields an empty result and no throw; a plist whose entries are
strings instead of dicts is skipped rather than trapping; importing the fixture and resolving it
reproduces `DefaultKeymap.bindings` for the 13 non-Spaces actions — which is the real assertion, since
that plist is where the defaults came from.

## Out of scope

Shortcut *sequences*, per-app shortcuts, and a menu-bar-clickable list of actions. Nothing in the
user's SizeUp workflow needs them.
